  THIS RUN DOES NOT DISTINGUISH WHAT IT WAS RUN TO DISTINGUISH.

  An earlier version of this section concluded "upscaled". That was wrong --
  not in the sense of being disproved, but in the sense of never having been
  supported. The reasoning is retracted and the reason it failed is worth more
  than the claim was.

  Csi2DataRateKbps is ONE slot, written on every CameraMIPIPHY_Start, read at
  teardown. A photo session runs at least two configurations -- preview, then
  the capture -- and the app drops back into preview the moment the shutter
  fires. So:

      hypothesis A: the still ran an index-1 mode. Reads 5485700.
      hypothesis B: the still ran mode 0, and preview overwrote it a second
                    later.                            Reads 5485700.

  The measurement is identical under both. It has no power to separate them.

  CsidRxTotalPktsRcvd = 9977 was cited as evidence for A ("too short for a long
  preview afterwards"). That argues the wrong way if anything: 9977 packets is
  about 3-4 frames, which is too few for a whole session including framing and
  capture, so the counter is very likely reset per stream-on. In that case it
  describes the LAST stream -- and 3-4 frames looks more like a brief
  post-capture preview than a capture sequence.

  TWO IMAGE-FORENSIC TESTS WERE TRIED. BOTH ARE BLIND. Recorded so nobody
  repeats them:

    1. Stop-band cliff. An upscale cannot contain detail above the source
       Nyquist; 3520->4032 predicts a cliff at 0.873. Positive control: the
       same image deliberately downscaled to 3520x2640 and back, re-encoded
       with the original's quantisation tables. The known upscale measured
       -1.1 dB and the real capture -1.2 dB. JPEG quantisation noise is
       broadband and fills the stop band, so the cliff is invisible even when
       it is certainly present.

    2. Resampling correlation. Interpolation leaves a periodic correlation at
       |1 - 1/1.14545| = 0.1270 cycles/sample in a second-difference residual.
       Fatally, JPEG's 8-pixel block grid sits at 0.1250. Known upscale +16.5
       dB, real capture +16.9 dB, and the "resample" and "jpeg-grid" figures
       came out identical -- the detector is measuring the block grid.

    Both were run with a positive control precisely so their blindness would be
    detected rather than mistaken for a result. That part worked.

  WHAT WOULD SETTLE IT: make the still the last stream before teardown. Take
  the photo and immediately hard-kill the Camera app (taskkill) so preview
  never restarts, then reboot and read. Nothing else on the Windows side
  distinguishes the two hypotheses, because the driver has one slot.

  WHAT IS UNAFFECTED: which mode the Linux side should stream. 3520x2640 and
  the other index-1 modes have a rate measured three times; 4032x3024's is

  FOUR measurements now, across every configuration reachable from Windows:
  video preview; photo preview + still; the Camera app at 4032x3024; and a
  preview-free 4032x3024 still. Every one reads 5,485,700 kbps.

  So: whatever sensor mode serves a full-resolution still on this device, its
  link runs at 2400 MSps, not the 1996.8 MSps that imx681.c's mode 0 register
  table implies (0x030d = 2, 0x030e/0x030f = 208, EXTCLK 19.2 MHz).

  THAT IS A CONTRADICTION AND IT IS NOT RESOLVED HERE. At least three things
  could explain it and this data does not choose between them:

    - the register table recovered as "4032x3024" is actually some other mode,
      i.e. the mode-to-table assignment made during the blob decode is wrong;
    - Windows never streams 4032x3024 off the sensor and the 12.19 MP output is
      produced from an index-1 mode;
    - op_sys_clk_div is not 1 for that mode specifically, which imx681.c's
      header already flags as an assumption.

  Do not pick one without evidence. What is measured is the rate.

  PRACTICAL CONSEQUENCE, and it is a simplification: there is no evidence of any
  second link rate on this part. Set cphy_datarate_kbps=5485700 explicitly on
  the Linux side rather than letting the driver derive it from link_freq. The
  parameter exists for exactly this, the value is measured four times, and it
  removes imx681.c's link_freq_menu_items from the path entirely.

  WORKFLOW: no reboot is needed. The driver reads CsiTestMode when the device
  context is created and writes the dump when it is torn down, and closing the
  capture app is enough for both. Arm, run, read -- seconds, not two reboots.
  Runs 1-3 each cost two reboots for no reason.

  Csi2CommonStatus1 = 0x20 is the first non-zero status word in any run. Windows
  saves it by name and this project has no bit definitions for it. Worth
  chasing: it is a working link reporting something, which is a better thing to
  decode than the Linux side's 00 04 01 on a link that does not work.

WINDOWS HELLO IS NOT CONTAMINATING THIS -- and the data says so itself

  Reasonable worry: Hello's face unlock runs at the login screen on the reboot
  between the camera session and the read, so its sensor could tear down last
  and overwrite these values.

  It does not, and the dump carries its own discriminator. Csi2PhaseCtrl0*,
  Csi2PhaseLnckCtrl0* and Csi2PhasePhyMode are written ONLY inside FUN_140006b50,
  which returns immediately unless is3Phase == 0 -- that is, only for a D-PHY
  device. It sets PhaseCtrl0Default 0x8e, PhaseLnckCtrl0Default 0x80 and
  PhasePhyMode 1 or 2.

  The Hello IR sensor (VD55G0) is D-PHY. So a dump left by Hello would show
  those fields non-zero. All three runs show them zero, which means the last
  teardown recorded was the C-PHY device -- the IMX681 -- every time.

  Keep checking them. Non-zero phase values mean the reading belongs to the IR
  camera and should be discarded.

READING NOTES  -- these are interpretation, unlike everything above

  Csi2DataRateKbps 5485700
      The measurement that mattered. 5.4857 Gbps against the 1.9968 Gbps every
      C-PHY run had programmed. Cross-checks against the sensor's own PLL
      registers: EXTCLK 19.2 MHz, op_pre_pll_clk_div 3, op_pll_multiplier 375
      -> op_sys_clk 2400.0 MHz, and 5485700000 / 2400000000 = 16/7 to five
      figures. So op_sys_clk is the C-PHY symbol rate and the data rate is
      symbols * 16/7.

  Csi2PhaseNumOfLanes 1
      Written from *(u8 *)ctx, the nNumOfDataLane field. One trio, stated by
      the vendor stack rather than inferred.

  Csi2PhasePhyMode, Csi2PhaseCtrl0*, Csi2PhaseLnckCtrl0*  all 0
      Not "the driver measured zero" -- these are set only inside FUN_140006b50,
      which returns immediately when is3Phase is set. Their staying 0 is itself
      a C-PHY confirmation, not a reading.

  Csi2PHYIndex 0
      UNRELIABLE. The write path remaps ctx+0x50 through a check on a value that
      must be 0x22b or 0x27b, and leaves the slot at its initialised 0 otherwise.
      Do not read this as contradicting camss's "phy 2".

  Csi2CommonStatus1/3/6/8  all 0
      Copied from the four globals the ISR fills. Zero across a working session
      is the known-good baseline the Linux side has never had -- it reads
      00 04 01 in three status words in every configuration.

  CsidRxTotalPktsRcvd 559179, CsidRxStatsEcc 0, CsidRxTotalCrcErrors 0
      A working link: half a million packets, no CRC errors. Note ECC is 0 here
      too, on a link that works -- so a 0 in that counter distinguishes nothing.

  CsidRxStats 23
      MEANING UNKNOWN, but narrowed by run 2: identical across two sessions
      whose packet counts differ by 65 %, so it is not a traffic counter.
      A register value or a fixed readback. Not yet traced. The coincidence
      with mission 11's 23-packet Linux run is exactly that.
